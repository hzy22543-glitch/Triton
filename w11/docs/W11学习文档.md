# W11 学习文档：让 Softmax 性能结论经得起追问

适用起点：你已基本掌握前 10 周，已写出 Triton 按行 Softmax，并完成正确性检查。本周沿用现有代码，把“能运行”推进到“能公平测量、解释收益、说明限制”。按相对周次学习，不需要等待原计划里的 11/30。

配套：[实验指导](W11实验指导.md)、[本地保存的 W10 算子实现](../src/w11_softmax/softmax.py)、[正式实验报告](../reports/W11实验报告.md)。本文是学习材料，文中的示例算术不代表你的 GPU 实测值。

## 1. 本周学完，你应能交付什么

用同一输入比较三种实现：朴素 PyTorch 表达式、`torch.softmax`、你在 W10 写的 Triton 实现。最低覆盖 4 类形状，保存正确性、预热后重复测量的中位数与波动、环境及原始数据，再写一份包含局限的报告。

你需要能回答四个问题：

1. 三者计算的是不是同一件事？
2. 计时到底包含哪些工作？
3. 在什么形状上更快或更慢，差异是否超过波动？
4. 为什么这组结果不能直接推出 vLLM 服务变快？

本周不要求固定加速比。全部慢于 `torch.softmax`，只要测量可信、解释诚实，也可以完成验收。暂不扩到 FlashAttention、GEMM、persistent 调度和自动调优。

## 2. 先把 W10 的知识接起来（30 分钟）

你的实现输入为二维连续 CUDA 张量 `x[M,N]`：M 是行数，N 是每行参与归一化的元素数。这里 M 可理解成一批独立行，**不一定等于模型的请求 batch size**；注意力中的 batch、head、query 维度也可能被展平成多行。

对每一行：

```text
m = max(x)
z = x - m
e = exp(z)
y = e / sum(e)
```

一个 Triton program 处理一行，`grid=(M,)`；块宽 `B=next_power_of_2(N)`。`N=1000` 时 B=1024，`N=1025` 时 B=2048。无效列加载为负无穷，指数为零，存储时再用 mask 限制有效列。

加载后转 FP32，归约与指数在 FP32 中进行，写回输入 dtype。当前支持 FP32/FP16、`1<=N<=4096`；不支持通用布局、反向传播与任意行宽。零行可返回空输出，但它不适合用于本周性能结论。

先合上代码解释：为什么 mask 不能只加在 store 上？为什么 FP16 转 FP32 不会找回输入已损失的精度？为什么 `BLOCK_SIZE=1024` 不等于启动 1024 个 CUDA 线程？答不顺时只回看 W10 对应段落。

## 3. 三种基线分别回答什么问题

| 实现 | 本周定义 | 比较用途 |
|---|---|---|
| naive | eager 的 max→减法→exp→sum→除法，多步张量表达式 | 观察减少中间张量和调用次数的价值 |
| torch | `torch.softmax(x, dim=1)`，现成框架算子 | 判断自定义实现是否优于可直接使用的方案 |
| triton | 原 W10 的 `triton_softmax(x)` | 验证你自己的具体实现，而非整个 Triton 的能力 |

**弱基线会夸大收益。** 假设 naive=60 μs、torch=12 μs、triton=15 μs：Triton 相对 naive 是 4 倍，但相对 torch 仅为 0.8 倍，实际比 torch 耗时多 25%。这三个数字只是算术例子。

不要把“比朴素写法快”改写为“比 PyTorch 快”。朴素表达式和 `torch.softmax` 都属于 PyTorch。

主性能表固定 eager、关闭梯度。另有设备侧诊断，两种实现均预分配输出，并在相同节点数的 CUDA Graph 中计时。Graph 摊销时间与 eager 结果对应不同的调用成本，分别解读。详见[实验报告](../reports/W11实验报告.md)。

FP32 是主实验。FP16 扩展中，配套 naive 会先转 FP32 运算，再转回 FP16，以匹配 W10 的中间精度约定；转换成本计入时间。不能拿这种 naive 的结果假装是“全程原生 FP16 表达式”的结果。

## 4. 融合为什么可能更快，又为什么不保证更快

### 4.1 从数据移动理解融合

按显式张量表达式估算，假设 FP32、暂不考虑缓存、编译器优化与最大值索引输出：

| 步骤 | 读元素数 | 写元素数 |
|---|---:|---:|
| 行最大值 | MN | M |
| 减最大值 | MN+M | MN |
| exp | MN | MN |
| 行求和 | MN | M |
| 除以行和 | MN+M | MN |
| 合计 | 5MN+2M | 3MN+2M |

因此朴素表达式的逻辑流量约为 `(8MN+4M)*4` 字节；理想融合版本只读一次输入、写一次输出，为 `2MN*4` 字节。M、N 较大时，二者的逻辑流量比接近 4。

这只是流量模型，**不是 4 倍实测加速承诺**。缓存命中、kernel 启动、指数和归约计算、并行度以及寄存器溢出都会影响时间。`torch.softmax` 本身已有优化，不能拿上述朴素流量直接代表它。融合的核心动机和算子结构可对照 [Triton Fused Softmax 教程的 Motivations 与 Compute Kernel](https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html)。

“数据留在片上”也不表示每个中间值都显式放入 shared memory。实际可能使用寄存器、warp 内通信或共享内存，由编译器与归约布局决定；不要仅凭 Python 源码推断精确存储位置。

### 4.2 按形状提出假设

| 条件 | 可能的影响 | 验证方法 |
|---|---|---|
| M 很小 | program 数少，GPU 并行度不足；主机调用成本可能占比较高 | 固定 N，对比 M=1、32、4096 |
| N 很小 | 每行工作少，封装/启动开销相对突出 | 固定 M，比较小中大 N |
| N 较大 | 归约工作和寄存器需求增加 | 对比 N=128、1000、4096，并用短 trace 辅助观察 |
| N 跨过 2 的幂 | B 突增，额外 lanes 参与计算/归约，mask 只保护访存 | 比较 N=1000、1024、1025 |
| 总数据较小且反复访问 | 缓存可能影响重复测量 | 报告输入复用策略，必要时另做轮换缓冲区实验 |

这些都是待检验的假设。看到 N=1025 变慢，可以说“与补齐开销假设相容”；没有资源指标或更直接对照，不能写“已证明寄存器溢出”。同样，不要仅凭 GPU 利用率就宣布带宽受限。

`num_warps` 更多也不必然更快：它可能加快行内工作，也可能增加资源消耗或减少同时驻留的工作。当前 W10 没有显式传入该参数，配套基准保持原调用方式；本周主实验先不调参。

## 5. 本周最重要的知识：你测到的到底是什么

### 5.1 GPU 异步执行

下面写法通常只测到 CPU 发起调用的时间，不能保证 GPU 已经算完：

```python
t0 = time.perf_counter()
y = triton_softmax(x)
elapsed = time.perf_counter() - t0
```

理解性写法应在计时前后同步：

```python
torch.cuda.synchronize()
t0 = time.perf_counter()
y = triton_softmax(x)
torch.cuda.synchronize()
elapsed = time.perf_counter() - t0
```

它可以用于理解，但单次结果容易受计时器、同步和系统调度影响。本周使用官方 `torch.utils.benchmark.Timer`，其 CUDA 测量会处理同步；`blocked_autorange` 自动选择一块里执行的次数，再采集多个计时块。[PyTorch Benchmark：同步与 Blocked Autorange](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)。

### 5.2 两种口径必须分开

| 口径 | 能回答的问题 | 注意事项 |
|---|---|---|
| 同步主机计时，反复调用后按次数摊销 | 在当前 Python 调用路径下，一次操作平均要多久 | CPU 提交和 GPU 执行可能重叠，不等于两者时间简单相加，也不是每次调用后都同步的单请求延迟 |
| CUDA Event 同一 stream 的时间间隔 | GPU 时间线上这段工作的耗时 | 可能含提交不及时导致的空隙；若包住多个 kernel，就不是单 kernel 时长 |

本周主表使用第一种。包括 Python 封装、输入元信息检查、输出分配，以及等待 GPU 完成的影响；输入创建、正确性检查、JIT 编译、显式预热、写文件和 profiler 不在计时范围内。

主性能基准中，所有候选都在函数内部创建输出。naive 的额外中间张量是它的实现成本，不应人为删除；也不能只给 Triton 预分配输出，却把 torch 的分配留在时间里，再声称公平比较。

如果以后只测 kernel，要给各方案明确一致的新接口和口径，另建表格。不能将 Event 数字与本周的主机计时数字直接计算加速比。

### 5.3 编译、预热与缓存

首次调用可能包括 CUDA 初始化、Triton JIT 编译、模块加载、分配器初始化等。应针对每种 shape/dtype/实现先验证，再显式预热，最后正式计时。预热不只做“整份脚本开头的一次”。

脚本对每个条件预热 25 次，并让 Timer 自行校准。25 次只是起点，不保证笔记本 GPU 温度与频率已进入稳态；还要观察多轮波动和独立复跑。

本周反复使用同一 GPU 输入，没有主动清缓存。它衡量的是这一复用策略下的调用性能，不代表每次从显存读取全新数据的冷缓存性能。不要在每次调用前 `empty_cache()`，那会改变实验问题；也不要把“清 PyTorch 分配器缓存”当成“清 GPU 数据缓存”。

### 5.4 环境也是实验变量

你当前实际设备是 RTX 4080 **Laptop GPU**，不是计划中的桌面 RTX 4080。驱动、PyTorch、Triton 以每次 `environment.json` 和 GPU 快照为准。

建议接电，记录系统性能模式；尽量让显示负载、温度与其他 GPU 工作稳定。不要为这次实验盲目升级已验证的环境。不同 dtype、不同机器、不同计时方式的数字分开报告。

## 6. 中位数、IQR、重复实验：该如何读数据

假设 Timer 某个计时块用了 100 次调用，总时间 1 ms，那么这个块贡献的是 `1ms/100=10μs` 的摊销样本。`raw_block_seconds` 保存块总秒数，除以 `number_per_run` 才是每次调用秒数。

脚本采用两层统计：

1. 每轮在一个条件上采集多个块，记录块均值的中位数和 IQR（P75−P25）。
2. 默认独立计时三轮，主表报告“三轮中位数的中位数”，另外保留轮间最小值、最大值。

同轮的加速倍率为：

```text
S_r = T_torch,r / T_triton,r
S_report = median(S_1, S_2, S_3)
```

`S>1` 表示 Triton 更快；`S<1` 表示更慢。报告倍率时同时保留绝对耗时：从 10 μs 到 5 μs 与从 10 ms 到 5 ms 都是 2 倍，但实际价值不同。

两个波动指标：

```text
轮内相对 IQR = IQR / 本轮中位数
轮间相对跨度 = (最大轮中位数 - 最小轮中位数) / 各轮中位数的中位数
```

若差异只有 2%，波动却是 15%，先写“当前证据不足以确认稳定收益”。三轮是课程最低测量设计，不是统计显著性保证。可把 10% 作为开始排查波动的工作阈值，但不要把它当成普遍统计标准。

这里的分位数来自**计时块平均耗时**，不是线上请求的 P95/P99，不能套用 W6/W7 的请求尾延迟含义。也不要删掉不喜欢的轮次；发现环境干扰应保留原记录、说明原因并另开一次运行。

## 7. 有效带宽如何算，如何不误读

统一用最小输入输出流量归一化：

```text
有效 GB/s = 2*M*N*element_size / elapsed_seconds / 1e9
```

例如 FP32 的 1024×1024，输入加输出为 8,388,608 字节；假设耗时 20 μs，则有效带宽约 419.4 GB/s。这里只是演算。

naive、torch、triton 都可用相同分子展示完成同一任务的效率，但 naive 实际有额外读写，所以这不是其物理 DRAM 带宽。反复访问缓存可能让这个指标大于显存标称带宽；不能据此宣称硬件超规格或认定数据必然错误。若要判断瓶颈，需要结合缓存策略、规模扫描和 profiler 证据。

本周优先看延迟与相对 torch 的倍率；有效带宽是辅助指标。

## 8. 算子更快，为什么整个服务不一定更快

若某算子原先占总耗时比例 f，算子提速 s 倍，在其余开销不变的理想模型下：

```text
整体加速比 = 1 / ((1-f) + f/s)
```

例如 f=0.1、s=2，整体仅约 1.053 倍；即使该算子无限快，整体上限也只有约 1.111 倍。这是 Amdahl 定律的简单应用，不是本周服务实测。

你的 Softmax 还没有集成进 vLLM。实际模型中的 Attention 可能已融合 Softmax，独立二维 Softmax 不一定存在可直接替换的调用点；还涉及布局、mask、精度和调度。只有完成真实集成并重新测量 TTFT、TPOT、吞吐等，才能讨论服务收益。

面试表达应是：“我实现了有限支持范围的行 Softmax，并在某环境、某形状集合、某计时口径下验证了收益与退化。”之后给出数据，避免泛称“优化了大模型推理性能”。
