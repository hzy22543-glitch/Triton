在 **WSL Ubuntu 的 Bash** 中运行：

```bash
cd w11  # from the repository root
```

复用已有 CUDA 环境，不需要新增运行依赖。`requirements.txt` 记录本机版本，不保证默认软件源能直接安装对应 CUDA wheel；全新机器需使用兼容的软件源，并重新验证。仅生成图片需要已有的 matplotlib，纯数据核验只用 Python 标准库。

记录实际电源模式和已知后台 GPU 任务。笔记本显示负载和系统调度可能影响结果；GPU 前后快照不是全程负载监测。无需停止不认识的系统进程，也不要把“看不到进程”误认为完全无负载。

## 2. 正确性先过关

```bash
python scripts/check_correctness.py
```

预期 `total=34, passed=34, failed=0`。用例含 FP32/FP16、非规则行宽、全负数、相等值、极大有限值、零行与接口拒绝。退出码非零即未通过，查看新建 `results/correctness/<时间>/cases.json`。

契约：CUDA、二维连续、FP32/FP16、行宽 1～4096、按 dim=1 做前向 Softmax；输出 shape/dtype/device 与输入一致。中间计算 FP32。有限值是验证范围，接口不会逐元素检查输入是否含 NaN/Inf；本项目不支持 autograd、任意布局和更宽行。

| dtype | 输出 rtol | 输出 atol | FP32 累加行和 atol |
|---|---:|---:|---:|
| FP32 | 1e-5 | 1e-6 | 1e-6 |
| FP16 | 1e-3 | 1e-5 | 1e-3 |

先处理失败用例，不通过随意扩大容限绕过问题。参考是相同输入上的 torch.softmax，不是数学精确真值。

## 3. 最低四类形状或完整九类形状

```bash
python scripts/benchmark_softmax.py --suite minimum --dtype fp32 --note '填写实际电源模式和后台负载'
python scripts/benchmark_softmax.py --suite full --dtype fp32 --rounds 3 --min-run-time 1 --note '填写实际条件；完整扫描'
```

两条命令可按需求选一条，不必每次全部执行。最低集合是 `(1,128)、(4096,128)、(1024,1000)、(1024,4096)`；完整集合额外包含 `(32,128)、(32,4096)、(1024,1024)、(1024,1025)、(4096,4096)`。

| 集合 | 每形状检查的实现 | 三轮计时组数 | 正确性检查数 |
|---|---:|---:|---:|
| minimum（4 类） | 3 | 36 | 12 |
| full（9 类） | 3 | 81 | 27 |

torch 与自身参考的检查只验证统一输出契约，不是额外的独立数值证明。每个形状验证通过后才开始计时；失败的运行不进入完整性能报告。

三个实现分别是 eager 多步张量表达式、torch.softmax 和本地 Triton 算子；不启用 torch.compile/CUDA Graph。FP32 为主实验。FP16 选做只需改 `--dtype fp16`，并单独分析；其 naive 会转 FP32 计算再转回 FP16，转换成本计入时间。

### 固定计时口径

- 同一个形状内，三个实现使用同一 GPU 输入；随机生成和校验在计时外。
- 关闭梯度；每个实现的输出与中间张量分配计入自己的时间。
- JIT 首轮和每条件 25 次显式预热在计时外；Timer 还会自动校准。
- 使用 `Timer.blocked_autorange` 同步主机计时；每轮轮转实现顺序。
- 反复调用后的总时间按调用次数摊销，CPU 提交与 GPU 执行可重叠，不是纯 kernel 时间或每请求延迟。
- 重用输入，不主动清缓存；不是冷缓存带宽测试。
- profiler、日志、结果写入不在正式计时内。

`--min-run-time` 是每实现每形状每轮的采样预算，不是调用次数或总脚本时长。默认 0.5 秒，正式复核使用 1 秒；自动校准可能仍产生较少计时块，需看 `sample_blocks`，不能只看到小 IQR 就认为结论可靠。

## 4. 核验数据与生成图表

```bash
python scripts/analyze_results.py
python -m unittest discover -s tests -v
# 可选，需要 matplotlib；显式指定运行可固定图表来源：
python scripts/analyze_results.py --plots --plot-run 20261115_000009_663517
```

纯分析不调用 GPU。脚本读取所有 `results/runs`，核验源码快照哈希、完整形状/实现/轮数、正确性记录、原始块统计和 JSON/CSV 汇总；发现失败、未完成或损坏记录就退出非零，而不是悄悄过滤。若自己的新运行被打断，先保存错误原因并排查，不手改它为 PASS。

输出为 `reports/数据核验与对照.md` 和 `reports/comparisons.json`；图表来源记录在 `reports/figures/source.json`。旧运行原文不会被改动。测试会复制记录到临时目录，验证篡改时间、缺失计时组、修改源码、正确性失败均能被拒绝。

核验正确性记录只说明记录完整且内部一致，不能在没有输出张量的情况下重证 allclose；真正的数值检查仍由第 2 步和基准前置检查执行。

### 手工检查一个值

`raw.json` 中每个计时块总秒数除以 `number_per_run`，再乘 `1e6`，得到 μs/调用。对块样本取中位数得到本轮耗时，再对各轮中位数取中位数得到主表耗时。

倍率分别用同轮 `naive/Triton`、`torch/Triton`，再对各轮比值取中位数。因此倍率不一定等于主表两个中位数直接相除。IQR 是块均值的 P75−P25，不是在线请求 P95/P99；跨运行结果不池化成一个大样本来掩盖漂移。

## 5. 解释收益、退化与异常

先看全量表，再选代表条件。已有正式报告覆盖：

1. 小形状相对 naive 有收益、相对 torch 却退化：弱基线不能代表现成框架算子。
2. 固定 N=4096，改变 M：收益受任务规模影响，不能推广为所有大张量都更快。
3. 固定 M=1024，比较 N=1024/1025：块宽翻倍不意味着墙钟时间翻倍，相对倍率也可能由 torch 自身变化造成。
4. 历史异常轮：中位数可能掩盖异常，必须看轮间范围和原始记录。

三轮是课程最低设计，不是统计显著性保证。轮间跨度或 IQR 超过 10% 可提示排查；这个阈值不是统计检验。环境不稳时保留原数据，独立重启脚本复测，不删除最慢那轮。

可选机制验证：

```bash
python scripts/profile_softmax.py
```

它预热后采集 32×128、1024×4096 各实现 5 次调用的短 trace，输出 GPU kernel 数量。用你已有的 trace 查看器打开 JSON。profiler 结果只用于观察执行结构，不填入正式延迟表；kernel 数少不保证墙钟时间更短，不能把时间差全部归因于调用次数。

## 6. 常见问题

| 现象 | 检查与处理 |
|---|---|
| 找不到 torch/triton，或 CUDA 不可用 | 使用 WSL 内已有 `.venv`；先确认 GPU 可用再安装/调整环境 |
| 输入行宽 8192 报错 | 超出本实现范围；扩展实现需另外验证 |
| 运行很久 | 总时长包括 JIT、校准和各条件采样；先看进度输出 |
| 正确性失败 | 查看 case/失败输入，检查 dtype、dim、mask，禁止靠删用例掩盖 |
| 数据核验失败 | 读报错对应运行；保留原始失败记录，核对缺失文件和版本 |
| 同一形状结果变化 | 对照版本、封装、功耗、显示任务、预热及所有轮次；不只比较最好值 |
| 全部慢于 torch | 如实报告支持范围和可能原因，不代表实验任务失败 |
