## 3. 实验一：证明 vector add 在边界上正确

### 3.1 先预测线程如何对应元素

当前 kernel 的索引为：

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) c[i] = a[i] + b[i];
```

`blockIdx.x` 是 block 编号，`blockDim.x` 是每个 block 的线程数，`threadIdx.x` 是 block 内线程编号。这里用一维 grid，每个有效线程处理一个元素。

在 blockSize=256 时，先自行填表：

| N | blocks=(N+255)/256 | 启动线程总数 | 不写结果的线程数 |
|---:|---:|---:|---:|
| 1 | 1 | 256 | 255 |
| 255 | 1 | 256 | 1 |
| 256 | 1 | 256 | 0 |
| 257 | 2 | 512 | 255 |
| 1000 | 4 | 1024 | 24 |
| 1025 | 5 | 1280 | 255 |

核对一个例子：N=257 时，2 个 block、512 个线程、255 个线程不写结果。线程仍会启动，只是条件分支不执行写入。

### 3.2 在 vector_add.cu 中完成修改

1. 将单次运行提取为 `bool run_case(int n)`，由 main 遍历上表六种长度。至少让 main 在任一用例失败时返回非零状态。
2. 改用随索引变化的输入，避免所有结果都等于 1000，漏算或错位更容易被发现。例如：

```cpp
a[i] = i % 17 - 8;
b[i] = (i * 3) % 23 - 11;
```

3. 删除 `cudaMemcpy(d_c, c, ..., cudaMemcpyHostToDevice)`。主机 c 尚未初始化，而且 kernel 将写入每个有效输出元素。
4. 从 `vector_bench.cu` 借用 `CUDA_CHECK`，给分配、拷贝、释放等 CUDA 调用检查返回值。
5. kernel 启动后，在这个正确性实验中明确检查：

```cpp
vector_add<<<numBlocks, blockSize>>>(d_a, d_b, d_c, n);
CUDA_CHECK(cudaGetLastError());
CUDA_CHECK(cudaDeviceSynchronize());
```

第一步检查启动错误；同步使异步执行错误在这里被发现。不要把这里的逐次同步机械地加进性能测试的每次循环。

6. 拷回后检查 **所有元素**。发现第一个错误，报告 n、i、实际值和期望值；成功才输出 `N=... PASS`。检查主机内存分配是否成功，并在正常和校验失败路径都释放资源。

可以参考这个检查片段，自己放到正确位置：

```cpp
bool ok = true;
for (int i = 0; i < n; ++i) {
    int expected = a[i] + b[i];
    if (c[i] != expected) {
        std::cerr << "N=" << n << " i=" << i
                  << " got=" << c[i] << " expected=" << expected << '\n';
        ok = false;
        break;
    }
}
```

### 3.3 编译和运行

完成上述修改后运行：

```bash
make build/vector_add_check
./build/vector_add_check 2>&1 | tee "$practice_dir/vector_correctness.txt"
```

若安装了 Compute Sanitizer，可额外验证越界；未安装不阻塞本周：


不要把“没有崩溃”或“输出前 20 个数正常”当作完整检查。可选：在临时副本中故意写错一次索引，确认测试确实会失败，然后恢复代码。

**验收：** 六种长度全部 PASS；能解释为何 N=1000 仍需 `i<n`；能区分正确性测试与性能测试。

## 4. 实验二：说清你到底测了什么

### 4.1 理解异步执行

CPU 调用 kernel 后，通常可以继续执行，GPU 工作可能尚未完成。直接用 CPU 时钟包住一次启动，可能主要测到提交工作所花的时间。

| 方法 | 测量范围 | 使用场景 |
|---|---|---|
| CPU 时钟，计时前后均同步 | 主机观察到的整个代码段耗时 | 端到端前向耗时 |
| CUDA Event，等待结束 event | 两个 event 在流上的时间间隔 | GPU 工作区间对照 |
| Profiler 中单个 kernel duration | 采样运行中的该 kernel 执行时间 | 定位耗时来源 |

Event 包围多次 Python 调用时，若 CPU 提交不及时，区间里也可能包含 GPU 空闲间隙，不能直接叫“所有 kernel 纯计算时间之和”。普通 `perf_counter()` 计时也不是 CPU 自身计算时间。

依据：[PyTorch CUDA 异步执行与计时说明](https://docs.pytorch.org/docs/stable/notes/cuda.html#asynchronous-execution)。阅读这一小节即可。

### 4.2 审查 vector_bench.cu

在代码上标出：内存分配 → 初始化 → 预热 → 同步 → start event → 重复启动 → end event → 等待 → 计算平均值。

回答并记录：

- 分配显存是否计入？当前没有。
- 主机与设备之间的数据拷贝是否计入？当前计时区间里没有这种拷贝。
- 当前输出的 avg 是否等于一次独立请求的延迟？不等于，它是连续多次启动的区间平均值。
- 零输入的程序能否证明输出正确？不能；原始版本没有读取和校验输出，当前版本已补充非零输入与全元素检查。

给这个 float kernel 补一个计时区间之外的非零输入正确性检查，再测量。可用小整数转 float 的输入，在本实验小数值范围内避免引入不必要的误差讨论。

```bash
make build/vector_bench
for n in 1024 262144 2097152 16777216; do
  for round in 1 2 3; do
    echo "round=$round N=$n"
    ./build/vector_bench "$n"
  done
done 2>&1 | tee "$practice_dir/vector_benchmark.txt"
```

每次执行顺序运行，不同时启动其他 GPU 基准。这里通过独立进程重复检查波动，进程启动本身不在程序的 event 区间内。

有效带宽口径：float32 两次读、一次写，逻辑字节数为 `3 × N × 4`，GB/s 为 `逻辑字节数 / 秒 / 1e9`。它是按算法访问量推算的指标，缓存命中会影响实际显存流量，不能直接当作物理 DRAM 带宽测量。

依据：[CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)，只查 Timing 与 Effective Bandwidth Calculation。

**验收：** 能解释为什么小 N 的有效带宽低，不仅考虑数据传输，还考虑启动开销与 GPU 工作不足；没有测量证据时不宣称“大 N 一定带宽受限”。

### 5.3 修改 attention_bench.py，使结果能复查

按以下顺序修改，每次改完先跑一种形状：

1. 创建随机张量前加 `torch.manual_seed(0)`。
2. 让 `bench` 返回 `results`，在调用处计算中位数，同时输出全部 5 轮数据。每个元素仍是“一轮 100 次前向的平均耗时”，不是单次调用延迟分布。
3. 每条记录保存 S、版本、测量组、轮次、repeats、时间单位和耗时。可保存 CSV，或先完整保存标准输出。
4. 保留 baseline → inplace → inplace → baseline 的执行顺序，重复 3 组，先检查顺序和热状态影响。
5. 最后加入 `S=128、512、1024`。每次 S 改变，都重新生成 q/k/v/mask 并运行正确性检查；不要只改数字而继续使用旧张量。

最小改动提示：把 `return statistics.median(results)` 改为 `return results`，相应将调用处改为：

```python
samples = bench(inplace)
print(name, 'round_us=', samples, 'median_us=', statistics.median(samples))
```

原函数内 `start.elapsed_time(end) * 1000 / repeats` 已经把毫秒换成微秒，不要再转换一次。

```bash
python benchmarks/attention_bench.py --output "$practice_dir/attention_rounds.csv" 2>&1 | tee "$practice_dir/attention_rounds.log"
```

建议整理：

| S | dtype | baseline 中位数 μs | inplace 中位数 μs | 各轮范围 | 耗时下降比例 |
|---:|---|---:|---:|---|---:|
| 128 | FP32 | 待测 | 待测 | 待填 | 待算 |
| 512 | FP32 | 待测 | 待测 | 待填 | 待算 |
| 1024 | FP32 | 待测 | 待测 | 待填 | 待算 |

加速比为 `baseline / inplace`；耗时下降比例为 `(baseline-inplace)/baseline`，两者不要混写。比较同样的形状、输入和统计口径，保留负收益。

### 5.4 如果波动很大，如何排查

上次复核出现 baseline 约 25.341 ms、2.175 ms，而 inplace 约 2.404 ms、1.992 ms。这组数据只说明该次运行不稳定，不提供可靠的固定加速比。上次验证期间还执行过其他检查，不能排除测量干扰，也不能据此归因于你的硬件或实现。

排查顺序：

1. 单独运行这个基准，不同时运行 vector add、profile、模型服务或其他 GPU 任务。
2. 记录笔记本插电状态、电源模式及后台 GPU 程序；用 nvidia-smi 查看 GPU 状态。利用率低也不能证明完全无干扰。
3. 保持同一 S，查看每轮数据和前后组是否持续变化。
4. 若怀疑预热不足，将预热从 20 次增加到 100 次，重新完整测量并记录这项变化，不从旧数据中挑最快值。
5. 若仍不稳定，记录现象和待验证原因，暂不汇报精确加速比。一次只改变一个排查条件。

**验收：** 输出一致、原始轮次可查、单位正确、没有 profiler；对稳定收益或不稳定现象都能如实说明。

## 6. 实验四：读懂现有时间线

优先使用已有 JSON 文件，不需要重新安装 profiler。使用已有 Chrome trace 查看器，或将文件加载到 [Perfetto UI](https://ui.perfetto.dev/)。找 CPU 线程、CUDA runtime、GPU stream 这几类轨道。

### 6.1 找四个范围和一次拷贝

在 baseline 中依次找到 `01_qk_matmul`、`02_scale_and_mask`、`03_softmax`、`04_av_matmul`。这些是 CPU 上的标记范围，不保证横向边界与 GPU 执行完全重合。结合关联事件与 GPU 轨道阅读，不按视觉位置猜调用关系。

上次对已有文件的解析结果，可作为查找提示：

| 观察对象 | baseline | inplace | 可以支持什么 |
|---|---|---|---|
| CPU 操作 | 有 clone/copy_ | 对应路径消失 | 实现路径减少了复制操作 |
| GPU DtoD 拷贝 | 约 108 μs | 对应拷贝消失 | 这份 trace 中省去一次设备内拷贝 |
| mask kernel | 约 57.5 μs | 约 57.5 μs | 本身执行时间没有明显变化 |

这些是已有单次 profile 的观察值，不是你今天的基准结果。不能将 CPU 操作总时长、嵌套子操作时长、GPU 时长、同步等待时长全加起来；它们可能包含或重叠。

思考：`scores` 的形状是 `[1,8,1024,1024]`，FP32 存储约 32 MiB。一次完整复制逻辑上需要读源、写目标，涉及约 64 MiB 的读写量，但这不自动等于实际 DRAM 流量。这个估算如何帮助你理解避免复制的意义？

### 6.2 读 kernel_trace.txt

选择连续 5 行，比较 `API Dur`、`Queue Dur`、`Kernel Dur`。单位 ns，除以 1000 才是 μs。

- API Dur：CPU 执行启动 API 的时长。
- Queue Dur：按该报告口径，提交后到 kernel 开始执行前的排队时长。
- Kernel Dur：GPU 上该 kernel 的执行时长。

如果 CPU 提交速度高于 GPU 消费速度，后续 kernel 排队时间可能越来越长，而每个 kernel 执行时间近似不变。这是待结合连续行验证的解释，不能把所有排队时长求和作为总运行耗时。
