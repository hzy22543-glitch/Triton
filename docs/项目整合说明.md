# W9～W11 轻度整合说明

## 1. 项目主线

整体主题为“CUDA/Triton 算子实现与性能分析”。W9 学习 GPU 基础与剖析，W10 完成 Triton 实现和正确性，W11 对 Softmax 做可信性能实验。三者是能力递进关系，当前没有形成一个共同执行的推理服务。

讲解顺序建议：先展示 W11 的三条基线与一个收益/退化条件，再解释 W10 的稳定化、mask 和精度，最后用 W9 的 trace 展示如何验证性能假设。简历中作为一个算子学习/性能分析项目展示，避免把相同 Softmax 分成重复成果。

## 2. 文件职责

```text
cuda_learning/
├── README.md                 # 总入口、展示重点、统一复现
├── scripts/verify_project.py # 检查现有证据，可选串行 GPU 回归
├── docs/                    # 整合说明与检查记录
├── reports/checks/          # 每次总检查的时间戳日志和源码哈希
├── w9/                      # CUDA 与 Attention 实验
├── w10/                     # Triton 实现与教学正确性
└── w11/                     # Softmax 性能对比、主要展示成果
```

单周项目仍可独立执行。当前 W9 名称为 `w9`；旧日志中出现 `w9_cuda` 是历史路径，不重写。总检查从脚本自身位置找目录，不依赖终端当前目录，也不全局安装这些实验包。

## 3. 维护规则

- W10/W11 的 Softmax 保持独立副本，以便单独学习和复现；本次没有引入跨目录导入或强制共用包。
- 后续算子性能改进优先落在 W11，改变实现后先过正确性，再重跑相关性能条件；旧数据继续关联旧源码快照。
- W10 vector add 本次只强化输入保护，不改变 GPU 计算公式；历史报告的 42 项与新回归的 48 项分别保留，不能回填历史数字。
- 各周数据目录保留原始样本、异常和失败；生成的新检查用新目录。不要仅为整洁删除源码快照。
- 对源代码的修正和新性能结论分别记录。文档路径变化、接口拒绝修正不等于已获得性能提升。

## 4. 测量口径对照

| 实验 | 计时口径 | 能支持的结论 |
|---|---|---|
| W9 CUDA vector add | CUDA Event 包围多次 kernel 启动，数据提前分配 | 该批量启动与缓冲复用条件下的时间 |
| W9 Attention | Event 包围多次 Python 前向，ABBA 顺序 | 同输入的普通/原地 mask 对照，可包含主机提交间隙 |
| W10 | 正确性实验，无性能基准 | 已覆盖输入范围内的数值与接口检查 |
| W11 Softmax | Timer 同步主机批量摊销时间，分配在函数内 | 当前 Python 调用路径下，三种实现的公平对照 |

两类计时不能直接相除作为 CUDA 与 Triton 的加速比。Profiler 用于机制观察，采样耗时不进入正式性能表；多个阶段存在 CPU/GPU 重叠，不把同步等待和 kernel 时间重复相加。

## 5. 统一检查覆盖与局限

默认检查文档链接和 Python 语法；检查 W9 已发布记录的 ABBA 完整性、CSV 数值与带宽公式，并在临时目录重新生成汇总和 trace 表比对；检查 W10/W11 已保存正确性计数；使用 W11 核验器从原始计时重算历史统计，并运行核验器的负向测试。

`--gpu` 额外强制重编译 W9、运行三周当前正确性，并用 `python -O` 检查 W10 vector add 的输入保护，验证 W11 拒绝 NaN/Inf 等非法计时预算。按顺序运行，完整输出保留到总检查目录。

默认检查通过只证明现有记录可核对，不证明当前 GPU 运行成功；后者需看 `gpu_requested=true` 的检查记录。正确性日志的离线一致性不是重新计算数值结果，历史源码哈希也不能证明记录来源真实。历史失败计数会保留在检查详情中，不被改写成 PASS 用例。

本次不重新测量全部性能，也不更新历史加速数字。W9 sanitizer、跨会话性能稳定性和个人理解验收仍按原报告保留限制。若未来需要服务层收益，另做实际集成和端到端测量。
