# W10 巩固学习：从索引推导到可信的 Triton Softmax

这份文档围绕本项目实际代码展开，跳过 Python 基本语法、张量创建等已熟悉内容。目标是能独立写出核心 kernel，说明每个参数的作用，并设计能发现错误的测试。代码均为前向计算，不实现反向传播。

建议分三次学习：第一次读第 1～5 节并手算索引；第二次读第 6～9 节并检查精度；第三次完成第 10 节练习，再读答案。约需 2～3 小时，可按理解情况调整。

## 1. 先明确代码在哪一层执行

阅读路径：[Softmax 源码](../src/w10_triton/softmax.py) → [vector add 源码](../src/w10_triton/vector_add.py) → [测试](../tests/correctness.py)。

```text
scripts/run_experiments.py
  └─ tests/correctness.py：创建输入、调用实现与参考、检查、留档
       └─ triton_softmax(x)：CPU 端 Python，检查和分配输出
            └─ softmax_kernel[grid](...)：向 GPU 提交计算
                 └─ 多个 program，各自计算一行
```

`@triton.jit` 标记的函数由 Triton 编译，不是普通 Python 逐条解释执行。Python 封装负责管理张量和启动计算，kernel 内通过指针访问设备数据。首次遇到需要编译的配置可能触发 JIT；之后可复用缓存，因此首次调用耗时不能直接当作稳定性能。

返回 `y` 表示拿到了输出张量对象，不意味着 GPU 此刻已经完成。后续同一 CUDA stream 上的操作按序执行；主机需要实际数值时，相关读取/检查可能引入同步。测试末尾显式同步有助于将执行错误暴露在当前用例中，但性能测量应另行设计。

项目现在分层的原因：源码只依赖 torch/Triton，测试依赖源码，脚本启动测试。不要让算子模块反过来导入测试，否则作为库使用时会产生不必要的耦合。

## 2. 写 kernel 前，先写下支持契约

本项目 Softmax 契约如下：

| 条件 | 为什么需要 |
|---|---|
| 二维 `x.shape == (M, N)` | 一个 program 对应一行，归约方向固定 |
| CUDA 张量 | 目标是 GPU kernel |
| 连续布局 | 使用 `row_id * N + cols` 定位元素 |
| FP32 或 FP16 | 当前已实现并验证的精度路径 |
| `1 <= N <= 4096` | 本练习约定的行宽上限，不是 Softmax 数学限制 |
| `M == 0` 可接受 | 空输出不需要启动 kernel |
| 有限输入是验证范围 | 未承诺 NaN/Inf 特殊语义，也未主动扫描拒绝它们 |

`N == 0` 与 `M == 0` 不同：前者没有参与归约的列，本实现拒绝；后者根本没有要计算的行，可以直接返回。

显式 `raise ValueError(...)` 用于接口条件，错误 dtype 用 `TypeError`。`assert` 更适合教学或内部不变量，`python -O` 会移除断言。Vector add 已在 2026-11-15 整合时改为显式异常检查，并补充了 6 个拒绝用例；不依赖 assert 保护接口。

## 3. Kernel 参数与启动参数：逐个对应

实际声明：

```python
@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, BLOCK_SIZE: tl.constexpr):
    ...
```

实际启动：

```python
n_rows, n_cols = x.shape
y = torch.empty_like(x)
block_size = triton.next_power_of_2(n_cols)
grid = (n_rows,)
softmax_kernel[grid](x, y, n_cols, BLOCK_SIZE=block_size)
```

| 名称 | 在哪里使用 | 含义与易错点 |
|---|---|---|
| `x` → `x_ptr` | 启动时传入，kernel 中访问 | 张量参数转换成设备数据指针；kernel 没有普通 PyTorch 张量方法 |
| `y` → `y_ptr` | 输出存储 | 在主机封装里先分配，kernel 写入；无需在 kernel 里返回 torch.Tensor |
| `n_cols` | 地址计算和 mask | 真实行宽 N；不是补齐后的宽度 |
| `BLOCK_SIZE` | `tl.arange` 的形状 | 每个 program 表达的数据元素数 B；本实现 B 为 N 向上补齐的 2 的幂 |
| `tl.constexpr` | 编译期 | 该参数作为编译时常量，可用于静态形状；改变它可能产生新的编译配置 |
| `grid` | 方括号中 | program 实例的启动网格，不是输入数据块，也不是线程数 |
| `n_rows` | Python 封装 | 决定 program 数；没有作为 kernel 参数传入 |

`n_cols` 没有标 `constexpr`，它是普通标量参数；但不能据此推断不同 `n_cols` 永远共用同一份机器码，JIT 还可能按参数属性特化。学习时先区分“声明为编译期参数”与“普通标量参数”，无需猜测缓存细节。

`grid=(7,)` 表示一维网格有 7 个 program；`tl.program_id(0)` 返回该维度上的编号 0～6。这里的 `0` 是网格轴号，不是 GPU 编号或线程号。

### BLOCK_SIZE、program、warp 之间是什么关系？

本项目采用传统 Triton 编程方式。在 NVIDIA 后端可将 program 理解为由一个 CTA 承担的工作单位，但一个 program 中的 B 个元素会分布给多个线程处理；不能把一个元素等同于一个线程。现代 Triton 还存在不同执行形式，不要把这句对应关系扩成所有模式的定义。

`num_warps` 是启动配置，控制每个 program 使用的 warp 数量，而 B 控制逻辑数据规模。NVIDIA warp 通常有 32 个线程；即使某配置使用 4 个 warp，也不意味着 B 必须为 128。线程可以处理多个元素，具体分配由编译器决定。

当前代码没有显式设置 `num_warps`，使用安装版本的默认配置。W10 不需要先调它；增加 warp 也不保证更快，归约、寄存器和并发驻留都会影响结果。

## 4. 从内存布局推导索引，而不是背公式

### 4.1 Softmax 的一行在哪里？

对于连续二维张量，行优先布局的 stride 为 `(N, 1)`。第 i 行第 j 列的元素偏移是：

```text
offset(i, j) = i * N + j
```

取 `(M, N)=(3, 5)`，处理 `row_id=1` 时 B=8：

```text
cols:       0  1  2  3  4  5  6  7
offsets:    5  6  7  8  9 10 11 12
mask:       T  T  T  T  T  F  F  F
```

偏移 10～12 仍可能落在整个张量内，但它们属于下一行，仍然必须屏蔽。mask 不只是防止越过整个 allocation，也保护“当前 program 的逻辑处理范围”。

指针加法以指向的数据类型的元素为单位。FP16 的 `x_ptr + 5` 已对应向后 5 个 FP16 元素，不要再手动乘 2；FP32 同理。

### 4.2 为什么转置不能直接用同一个公式？

原始 `(3,5)` 连续张量转置后 shape 为 `(5,3)`，stride 为 `(1,5)`。通用元素偏移应为：

```text
offset(i, j) = i * stride(0) + j * stride(1)
```

如果仍使用 `i * 3 + j`，读到的物理位置与逻辑张量不同。支持非连续布局必须传入 stride 并正确计算地址；还要决定输出布局和存储地址。调用 `.contiguous()` 是复制成新布局，复制开销必须纳入后续性能口径，不等于原 kernel 原生支持任意 stride。

### 4.3 Vector add 为何是另一个公式？

其一维输入按固定大小切块：

```python
pid = tl.program_id(0)
offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
mask = offsets < n_elements
```

`n_elements=257, BLOCK_SIZE=256` 时，`triton.cdiv(257,256)=2`。第二个 program 表达 256～511 的偏移，仅偏移 256 有效。Softmax 不按整个张量这样切块，是因为归一化必须在每行内部完成，不能把两行数据混到同一次归约。

## 5. Softmax kernel 逐步拆解

下面是当前源码的等价精简版，适合闭卷重写；完整注释见源码。

```python
@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, BLOCK_SIZE: tl.constexpr):
    row_id = tl.program_id(0)
    cols = tl.arange(0, BLOCK_SIZE)
    mask = cols < n_cols
    offsets = row_id * n_cols + cols
    row = tl.load(x_ptr + offsets, mask=mask, other=-float('inf'))
    row = row.cast(tl.float32)
    shifted = row - tl.max(row, axis=0)
    numerator = tl.exp(shifted)
    denominator = tl.sum(numerator, axis=0)
    result = numerator / denominator
    tl.store(y_ptr + offsets, result, mask=mask)
```

| 中间变量 | program 内逻辑形状 | 含义 |
|---|---|---|
| `cols / mask / offsets` | `[B]` | 列编号、是否有效、元素偏移 |
| `row` | `[B]` | 有效元素 + 填充值 |
| `tl.max(row, axis=0)` | 标量 | 当前 program 中这一行的最大值 |
| `shifted / numerator` | `[B]` | 平移后的值、各元素指数 |
| `denominator` | 标量 | 当前行指数之和 |
| `result` | `[B]` | 包含 padding 槽位的中间输出 |

`axis=0` 在这里针对的是 program 内一维 `row`，不是原始 torch 张量的第 0 维。原张量按列归一化写 `torch.softmax(x, dim=1)`，Triton 这里仍写 `axis=0`，二者并不矛盾。

标量最大值、分母分别广播到 `[B]`。不同 program 不需要通信，因为不同行的 Softmax 彼此独立；一行内部的归约由 Triton 生成相应线程协作代码。

### 5.1 `tl.arange(0, B)` 不是普通 Python range

它生成 kernel 内的逻辑索引张量，而不是在 Python 中循环 B 次。这里使用从 0 起、B 为 2 的幂的静态范围 [2]。例如 N=257 时 B=512；实际只读 257 个有效元素，但计算表达式包含 512 个槽位。这种补齐成本是将来性能分析的一部分。

### 5.2 `tl.load(pointer, mask, other)` 的参数

- `pointer`：本例为 `[B]` 个地址，决定从哪里读。
- `mask`：同形状布尔条件；false 的位置不执行对应读取。
- `other`：没有读取的位置在返回结果里取什么值；省略时无效位置的值未定义，不能让它参与本例归约 [3]。

`other` 会转换成被读取元素的类型，随后 `.cast(tl.float32)` 将整块值转换为 FP32。`-inf` 可由 FP16/FP32 表示。

读取 mask 不会自动传给后续运算，也不会自动保护 store。最终仍需 `tl.store(..., mask=mask)`：false 的位置不写入。不能先无保护地读取，再用后续选择表达式“补救”，因为错误访问已经发生。

### 5.3 为何 Softmax 的填充值必须与归约相匹配？

考虑真实一行 `[-2,-1,-3]`，B=4。正确填充为：

```text
row       = [-2, -1, -3, -inf]
max       = -1
shifted   = [-1,  0, -2, -inf]
exp       ≈ [0.3679, 1, 0.1353, 0]
sum       ≈ 1.5032
```

若填 0，则最大值为 0，且多出 `exp(0)=1` 进入分母。即使只存前 3 个位置，它们也已经被错误分母缩小。问题的根本是 padding 参与了归约；换一个公共平移量本身在精确数学中不改变有效元素间的归一化结果。

Vector add 只有逐元素运算，不同槽位不相互归约，无效结果又被 store mask 丢弃，所以填 0 是合理的。可推广的原则是：求和常用 0、求最大常用负无穷、求最小常用正无穷；要按完整计算链选择，不能机械套用。

## 6. 数值稳定和精度：必须能解释的部分

### 6.1 减最大值的推导

对任意公共常数 c，在实数精确运算下：

```text
exp(x_j-c) / Σ_k exp(x_k-c)
= [exp(x_j) * exp(-c)] / [exp(-c) * Σ_k exp(x_k)]
= exp(x_j) / Σ_k exp(x_k)
```

选择 c=max(x) 后，每个移位值不大于 0，至少一个是 0；指数不大于 1，且至少有一个为 1，所以有限行不会因为所有指数都极小而使分母变成 0。`[1001,1002,1003]` 被转换为 `[-2,-1,0]`。核心稳定化思路见官方 Softmax 教程 [1]。

非常小的指数仍可能下溢到 0，这是浮点表示的限制；`tl.exp` 也是近似计算，不保证与 PyTorch 逐位相同。全为 `-inf` 的行会出现 `-inf - (-inf)`，不能用“减最大值”宣称自动解决全部非有限值。

### 6.2 FP16 → FP32 → FP16 的三个阶段

```text
原始数学值 → 存成 FP16 输入 → FP32 中间运算 → FP16 输出
               已有量化         减少累计误差       再次舍入
```

`torch.empty_like(x)` 决定输出 dtype。FP16 输入对应 FP16 输出，`tl.store` 写回时将 FP32 结果转换成目标类型。中间 FP32 能减少求和和运算误差，但不能恢复输入量化前的细节，也不能让 FP16 输出具有 FP32 的表示精度。

因此比较时应把同一份 FP16 输入交给两种实现。若一个实现输入原始 FP32，另一个输入其 FP16 转换值，比较就混入了输入变化。

### 6.3 为什么行和要用 FP32 累加？

```python
row_sums = actual.float().sum(dim=1)
```

这里先把**已经存下来的**概率转成 FP32 再求和，以更细的输出精度观察行和偏差。它不能消除各 FP16 概率已有的舍入。直接得到 FP16 行和可能将一个接近 1 的值再次舍入成 1，掩盖偏差。

本次报告中 FP16 最大行和误差约 2.44e-4，小于预设 1e-3；FP32 最大行和误差约 2.38e-7。数字只对应报告引用的运行，不是未来所有输入的误差上界。

## 7. 如何写能发现错误的测试

### 7.1 对照与不变量分别在检查什么？

```python
actual = triton_softmax(x)
expected = torch.softmax(x, dim=1)
torch.testing.assert_close(actual, expected, rtol=rtol, atol=atol)
```

逐元素对照检查具体概率是否一致；行和接近 1、概率非负且有限是额外不变量。只检查行和是不够的：将每行概率顺序打乱、甚至统一输出 `1/N`，都可能满足行和要求，却不等于输入的 Softmax。

`assert_close` 的数值条件是：

```text
abs(actual - expected) <= atol + rtol * abs(expected)
```

FP16 设 `rtol=1e-3, atol=1e-5`，若参考值为 0.5，允许差约为 5.1e-4；若参考值为 1e-7，允许差约为 1.00001e-5，绝对容限主导。这解释了为什么测试通过不代表所有极小概率相对误差都小。

FP32 使用 `rtol=1e-5, atol=1e-6`；行和的参考值固定为 1，直接设 `rtol=0`，使用明确的绝对误差预算。容限在运行前确定，失败后先定位，不应根据输出随意放宽。

### 7.2 每类用例对应哪个风险？

| 用例 | 想发现的问题 |
|---|---|
| `(1,1)` | 最小归约，输出应为 1 |
| 255 / 256 / 257 列 | 2 的幂前后 padding 和块宽变化 |
| 1000 列 | 较长不规则行 |
| 4096 列 | 当前约定上界 |
| `(1024,257)` | 多 program 的行定位 |
| 全负数且不规则行宽 | 错误填 0 参与归约 |
| 全相等 | 应接近均匀分布 `1/N` |
| 大正偏移 | 是否做了稳定化 |
| 重复最大值与极端有限值 | 归约及概率集中情形 |
| `(0,5)` | 空张量分支，无需执行 kernel |
| 转置、CPU、FP64 等 | 是否在启动前给出正确拒绝原因 |

Softmax 数值用例每种 dtype 为 13 个，另有每种 dtype 的空输入，共 28 项；加 6 类拒绝测试为 34 项，再加 8 项 vector add 数值测试和 6 项拒绝测试，当前总共 48 项（历史报告为 42 项）。

### 7.3 测试辅助函数里的参数为什么这样写？

`tests/correctness.py` 中 `check(...)` 将重复检查集中起来：

| 参数 | 用途 |
|---|---|
| `name` | 标识场景；与 shape/dtype 一起识别结果 |
| `x` | 元信息检查、输入留档 |
| `operation` | 不带参数的可调用对象，执行待测实现 |
| `reference` | 不带参数的参考计算；拒绝用例不需要它 |
| `expected_error` | 期望异常类型，避免任何异常都被算作成功 |
| `message` | 验证具体拒绝原因，防止错误分支碰巧抛同类型异常 |
| `other` | vector add 第二个输入，用于失败留档 |

例如 `lambda: triton_softmax(x)` 暂不计算，而把计算交给 `check` 的异常捕获范围。当前循环中立即调用 `check`，因此捕获当前 x 没问题；如果以后把这些 lambda 存到列表、循环结束后再执行，就要注意 Python 闭包对变量的后绑定，可用默认参数绑定当前值。

空输入不能计算 `.max()`，因此先判断 `numel()`；元信息和空输出对照仍要做。非空结果先转 FP32 再计算差，避免用低精度差值观察低精度误差。

SHA256 用于检测源码内容变化，不是“正确性证明”。旧记录的路径和哈希对应旧布局，应保留；重排文件后生成新记录即可。CUDA 严重非法访问可能使设备上下文不可用，不能保证异常处理中的 `.cpu()` 仍成功，此时应保留日志并重启进程排查。

### 8.1 它是“调试脚本”吗？需要掌握到什么程度？

可以把它理解为帮助发现错误的脚本，更准确的名称是**自动化正确性测试程序**。它自动生成输入、执行自己的实现、执行参考实现、判定是否通过，并保存证据。发现失败后，再根据报错去调试索引或数值计算。它本身没有断点、单步执行、变量交互查看等调试器功能，也没有性能测试功能。

命令行只是配置入口；目前只能选套件、种子和输出目录，不能通过参数任意指定 shape、dtype 或 BLOCK_SIZE。这些仍在用例列表和算子源码中定义。文件放在 `tests/` 不代表它一定由 pytest 驱动，本项目使用自定义测试循环。

| 掌握层次 | 内容 | 自检标准 |
|---|---|---|
| 必须能独立写 | 生成一个输入、调用自己的算子、调用参考、按容限比较 | 不看完整脚本，写出下面的最小检查 |
| 必须能解释 | shape/dtype/device、空输入、行和、正向与拒绝测试 | 能说清“报错有时为什么是 PASS” |
| 必须会使用和修改 | `--suite`、`--seed`、用例列表、查看失败记录 | 能新增一个 `(8,513)` 测试并找到对应结果 |
| 需要看懂，暂不必熟练设计 | 函数作为参数、lambda、闭包、try/except/else | 能跟踪一次 check 调用，不混淆张量与函数 |
| 了解用途即可 | SHA256、时间戳、subprocess、平台信息、JSON 排版 | 知道为什么保存，不要求背 API |

本周优先掌握的是“如何证明算子在给定输入上算对”，不需要为了学 Triton 先写出通用测试框架。

### 8.2 先看去掉所有工程包装的最小版本

下面是完整脚本中一个正向测试的核心逻辑，供阅读或在配置好 `src` 导入路径的环境中练习：

```python
import torch
from w10_triton.softmax import triton_softmax

x = torch.randn((7, 257), device='cuda', dtype=torch.float32)
actual = triton_softmax(x)             # 自己的实现
expected = torch.softmax(x, dim=1)     # 相同输入上的参考
torch.testing.assert_close(actual, expected, rtol=1e-5, atol=1e-6)

row_sums = actual.float().sum(dim=1)
torch.testing.assert_close(
    row_sums, torch.ones_like(row_sums), rtol=0, atol=1e-6,
)
print('PASS')                         # 前面的检查不抛异常，才会执行到这里
```

如果将片段保存为项目根目录下的临时文件，例如 `scratch_check.py`，可在 WSL 项目根目录用 `PYTHONPATH=src python scratch_check.py` 运行。正式套件使用 `scripts/run_experiments.py`，它自动处理此导入路径。这个片段是讲解材料，不是新增的已执行实验。

add 的核心只需把 `actual` 换成 `triton_add(x,y)`，把 `expected` 换成 `x+y`；输入必须满足一维连续 FP32 契约，而且不检查概率行和。其余版本记录、循环、文件保存都是在核心验证外逐层加上的。

### 8.3 一条命令怎样执行到一个 Softmax 用例？

```bash
python scripts/run_experiments.py --suite softmax --seed 42
```

执行顺序如下：

1. 入口脚本将 `src/` 加入当前进程的模块搜索路径，使 `from w10_triton.softmax import ...` 能找到源码。
2. `runpy.run_path(..., run_name='__main__')` 执行测试文件，使其末尾的 `if __name__ == '__main__'` 生效，调用 `main()`。
3. `main(argv=None)` 中，`parse_args(None)` 从命令行解析选项，得到 `args.suite == 'softmax'`、`args.seed == 42`。如果手动调用 `main(['--suite','softmax'])`，则解析传入列表。
4. 检查 CUDA、创建结果目录、设置种子、保存环境，定义内层函数 `check`。**定义函数时不会执行函数体中的算子。**
5. `args.suite` 不属于 `('all','vector_add')`，所以跳过 add；进入 Softmax 的 dtype 和 shape 循环。
6. 创建当前输入 x，调用 `check(...)`，完成这一例后再创建下一例。最后汇总共 34 项 Softmax 检查。

`--output-dir` 对应属性名 `args.output_dir`，因为 argparse 将选项中的连字符转换成下划线。`type=Path` 把字符串变为路径对象；`type=int` 把 seed 字符串变为整数。`choices` 拒绝未知套件名，`default` 在省略参数时提供默认值。

可先执行 `python scripts/run_experiments.py --help` 查看参数；它会输出帮助并退出，不启动实验。

### 8.4 最容易卡住的地方：operation、lambda 和两层异常捕获

实际用例写法：

```python
check('softmax_random', x,
      lambda: triton_softmax(x),
      lambda: torch.softmax(x, 1))
```

等价于以下写法：

```python
def run_actual():
    return triton_softmax(x)

def run_reference():
    return torch.softmax(x, 1)

check('softmax_random', x, run_actual, run_reference)
```

这里传入的是函数，**没有括号**；`check` 内部执行 `operation()` 和 `reference()` 时，才实际计算。若写成 `check(..., triton_softmax(x), ...)`，计算会提前发生，而且参数变成张量，之后 `operation()` 不能按预期调用。延迟执行还让算子抛出的错误落在 `check` 的异常捕获范围内。

`check` 定义在 `main` 里面，因此可以访问外层 `out` 和 `records`；这称为闭包。`records.append(...)` 是修改现有列表，不需要 `nonlocal`。这一组织方式减少参数传递，并不是 Triton 的特殊规则。

**正向用例的执行路径：**

```text
没有 expected_error
→ operation() 得到 actual
→ reference() 得到 expected
→ 检查输出元信息
→ assert_close 逐元素比较
→ 非空时统计误差，并按 softmax 前缀检查概率不变量
→ GPU 同步
→ PASS
```

其中任何检查失败，异常进入最外层 `except Exception`，记为 FAIL 并尝试保存输入。`name.startswith('softmax')` 是当前实现的一个约定：新增 Softmax 测试时保留这个前缀，否则不会执行专用概率检查。

**拒绝用例的执行路径：**

例如传入 `(2,0)`，要求 `ValueError` 且异常信息包含“行宽”：

| 实际情况 | 内层发生什么 | 最终结果 |
|---|---|---|
| 抛 ValueError，包含“行宽” | 被预期的 except 捕获，原因检查通过 | PASS |
| 完全没有异常 | 进入 try/except 的 else，主动抛 AssertionError | 外层记录 FAIL |
| 抛 ValueError，但原因不符 | 原因检查抛 AssertionError | 外层记录 FAIL |
| 抛其他异常类型 | 内层不匹配，异常向外传播 | 外层记录 FAIL |

`except expected_error` 中的变量保存的是异常类，例如 `ValueError`，不是字符串 `'ValueError'`。内层处理“预期的拒绝”，外层处理“测试失败”；两者目的不同。`else` 属于紧邻的 `try/except`，表示 try 没抛异常，并不是 `if expected_error` 的 else。

### 8.5 学会看结果，而不是只看有没有打印 PASS

每例产生一个 `record` 字典。成功或失败后，它被追加到 `records`，并写入 `cases.json`。遇到普通可捕获失败时，程序仍可能继续打印后面的 PASS，因此应先看最终 `failed`，再定位失败用例。

```python
failed = sum(r['status'] == 'FAIL' for r in records)
return 1 if failed else 0
```

上面将每个条件的 True/False 按 1/0 累加。末尾 `raise SystemExit(main())` 将返回值变为进程退出码；在 Bash 中运行后立即执行 `echo $?`，0 表示本次套件通过，1 表示已汇总到测试失败。参数错误或 CUDA 不可用会提前终止，也会是非零，不能假定所有非零都对应 cases.json 中的数值失败。

排查顺序：先看 `summary.json` → 在 `cases.json` 找 `status: FAIL` → 看 name/shape/dtype 与 traceback → 判断是接口、数值还是环境错误 → 必要时用保存的输入重现。修复后重新运行，保留旧数据；不要直接删除失败记录或扩大容限。

首次学习可以按以下顺序阅读注释版代码：**⑤ 用例循环 → ④ check → ① 参数解析 → ⑥ 汇总 → ②③ 运行准备和环境记录**。不必从 import 开始逐行背到最后。

小练习（待你完成，不计入当前 48 项检查）：在随机形状列表加入 `(8,513)`，预测两种 dtype 会新增几项检查，并说明 B=1024 时的 padding 数。答案：全套增加 2 项至 50 项，每行 padding 为 511 个；不要只改报告数字，应实际跑完后再记录新结果。

## 9. 从 W10 过渡到 W11：现在应理解什么

融合意味着把减最大值、指数、求和、除法放到一个 kernel 中，减少中间张量落到全局内存及多个 kernel 启动的机会。但 `torch.softmax` 本身已经是优化算子，不能将多个朴素 PyTorch 操作的开销当成 PyTorch Softmax 的必然开销。

当前代码只表达“一次加载输入、在 program 内计算、一次写出”的设计目标；实际寄存器分配、spill、缓存和访存效率需要编译与剖析证据，不能仅凭源码保证所有中间值永远留在寄存器。

W11 需要统一比较三者：朴素表达式、`torch.softmax`、本实现。排除首次编译、做预热、同步或使用正确的 GPU 计时工具、重复测量，并统一是否包含输出分配。不要用现在含 JSON 写盘、`.item()` 和正确性检查的整个测试脚本耗时作为 kernel 性能。

### 练习 B：闭卷补全核心六步

### 练习 C：安全观察错误填充值

在 PyTorch 中分别计算 `softmax([-2,-1,-3])` 和 `softmax([-2,-1,-3,0])[:3]`，观察后一组的和为何小于 1。这个练习模拟填 0 后只存有效列的结果，无需移除 GPU 访存 mask 来制造非法访问。

### 练习 D：设计变形测试

用 FP32 输入验证 `softmax(x + c)` 与 `softmax(x)` 接近，并验证列置换后输出做相同置换。先使用小整数 c 和温和输入；在 FP16 下很大的 c 会改变输入量化，不能要求任意偏移逐位不变。

### 练习 E：扩展设计，不急着实现

### 练习 F：讲清精度与容限

回答：为什么输入转换成 FP32 不等于 FP32 输入？为何 FP16 行和用 FP32 求？`atol` 会如何影响极小概率测试？

### 参考答案与验收

- A：7 个 program；B=512；编号 2 的行起点为 `2*257=514`；每个 program 有 255 个 padding 槽位。
- B：重点核对地址乘真实 N，而非 B；归约轴是 program 内的一维轴；load 与 store 均带 mask。
- C：多出来的 0 贡献指数 1，分母增大；最后丢弃一个输出不会撤销分母影响。
- D：这是数学性质的辅助检查，仍需数值容限和参考实现；不能替代全部测试。
- E：输入地址为 `i*s0+j*s1`；若输出新建连续张量，存储地址为 `i*N+j`。必须独立考虑输入与输出布局，测试转置、步长切片和不规则行宽。
- F：输入已量化；FP32 求和更准确地观察存下的概率之和；接近 0 时绝对容限主导，可能放过很大的相对误差。
